# STM32 运动命令失败定位与复测（2026-10-17）

仅修改 STM32 固件、固件回归和说明文档，没有修改 ROS。CAN 速率、ID、数据长度、字节定义和电机地址 1～4 均保持兼容。

## 原版本的源码结论

### 实体按钮的三个结果不是同一个阶段

`main.c::Buttons_Service()` 消抖后分配序号，调用 `motor_request_local_sync_start()`。
该函数只检查近期 ROS 活动和本地启动槽是否占用，登记一个待执行的 `cmd=05`。
因此第一条 `0x112/result=0` 只表示登记成功，不表示缓存已就绪、同步指令已发出或四轮已起转。

电机任务优先处理普通命令队列，队列排空后才取本地启动槽。原版
`motor_trigger_sync_motion()` 有以下具体拒绝条件：

| 分支 | 返回条件 | 底层结果 |
|---|---|---|
| 缓存完整性 | `staged_mask != 0x0F` | `HAL_ERROR` |
| 缓存时效 | 任一 `now - staged[i].tick > 500 ms` | `HAL_ERROR` |
| 位置参考 | `slot_to_speed()` 无法获得有效的位置模式/参考 | `HAL_ERROR` |
| 安全检查 | `collision_blocks(rpm)` 为真 | `HAL_ERROR` |
| 发送提交 | `zdt_trigger_sync_start()` 非 `HAL_OK` | 保留其返回值 |

这些分支汇入 `reject → collision_stop()`，取消待发运动、清缓存并广播 `FE 98 00 6B`。
因此按键后地址 1 的 `FE 02 6B` 与拒绝后停车吻合，不能作为同步触发成功的证据。
另外，`motor_process_next_command()` 原先还会拒绝在主队列等待超过 500 ms 的启动命令，返回 `HAL_TIMEOUT`。

原电机任务把任何非 `HAL_OK` 统一编码为 `0x102/result=1`；如果来源是实体按钮，再发送
`0x112/result=2`。原 `motor_apply_command()` 同时增加一次 `exec_fail_count`。
所以 `1504/05/01` 和后续同序号 `0x112/result=2` 是同一次执行失败的两种报告，
不是前一条 ACK 已成功之后又由电机报告一次失败。

500 ms 运行命令租约被错误复用于等待人工按键的缓存，是可复现的软件缺陷。
但本次旧日志没有缓存时间、掩码及安全拒绝原因，不能唯一证明实车 `0x1504` 命中的就是缓存过期。

### 即时速度失败是另一条入口

`0x100` 为命令分配序号并入队。原 `submit_motion()` 对每一轮 `sync=0` 指令：

1. 从 `requested_rpm` 复制另外三轮旧目标，替换当前一轮。
2. 用这个新旧混合组合执行 `collision_blocks()`。
3. 若位置换算或安全检查失败，广播停车并返回 `HAL_ERROR`；否则调用 `zdt_motor_set_speed()`，其提交失败也会停车并返回原状态。

生产矩阵中 `wz = -c/(4L) × (motor0+motor1+motor2+motor3)`。
例如完整横移 `[25,0,-25,0]` 的角速度为零，逐轮更新时第一个非零轮却产生暂时的转向请求。
前方 90 mm 时，旧实现会在完整横移到齐之前触发 100 mm 转向保护。
原有生产矩阵测试甚至明确要求这种拒绝发生；本次改为验证四轮到齐后的同批即时请求。

低至 5～10 RPM 仍可能触发该分支：固件最小平移停车距离为 150 mm，转向停车距离为
100 mm，并考虑有效的实际速度反馈及侧/后传感器安装内缩。目标速度小不是保护必然放行的条件。

旧 `cmd=01` 的其他非成功条件还包括：主队列命令过期、参数/索引错误、心跳超时、
电机故障、未配置运动学、停车尚未成功及底层提交拒绝。
给定最后一帧的 `idx=2/-5/accel=50/sync=0` 本身参数有效，但它与负 ACK 的时间邻近，
不能证明它就是序号 `0x1F79` 对应的入队项。旧固件没有把该序号、索引和具体失败原因持久记录下来。

**判断：缓存生命周期错误与逐轮混合向量校验是两个独立缺陷；二者共用安全拒绝和停车路径，
但不能从两条二值负 ACK 推断它们共享某个唯一底层根因。**

### 队列、应答和 HAL 状态核查

原 ZDT 层已有异步队列：等待另一命令应答时，成功入队会返回 `HAL_OK`，并不是一律返回
`HAL_BUSY`；不能把这两次实车失败直接归因于“异步未完成被当作失败”。

真正的问题是原上层在 ZDT 入队时就发送成功 ACK、增加执行成功计数；后续 `E2/EE`
只清等待槽，运动应答超时则丢弃当前项后继续调度，均没有关联回原命令终态。
原匹配已有地址、功能码、帧格式和硬件 TXOK 检查，但把 `9F` 旧动作完成也当作新命令的确认。

## 本次修改

- 四轮 `sync=0` 速度在最多一个控制周期（10 ms）的窗口内收集，以完整候选向量校验一次。
  满四轮立即提交；单轮/不完整组到窗口边界按实际已收到的组合校验；重复索引或不同类型命令形成边界。
  下发仍是原生即时 F6，`sync=0`，不合成 `05` 或实体按钮事件。
- 缓存确认后可在持续正常心跳下等待按钮。缓存不再消耗运行指令的 500 ms 租约；
  同步触发时开始运行租约。队列命令和运行中活动轮的 500 ms 超时保留。
  心跳失效、急停、故障或失败会使缓存失效；新缓存代必须重新提供四轮。
- 电机任务每毫秒推进异步事务。每个底层请求携带内部 tag，关联到原命令序号、类型和索引；
  只在终态输出一次 ACK、更新一次执行统计。参数、profile、心跳等本地命令完成本地处理后输出终态。
- 默认 WAIT_ACK 下，F6/FB 等运动等待匹配地址的原生 `02`。同步广播仍向地址 0 发
  `FF 66 6B`，按手册的广播返回规则，等待地址映射第一项（默认物理地址 1）的 `FF 02 6B`；
  不要求广播对四轮分别回包，也不把地址 2～4 的应答关联到地址 1。
  这证明驱动接收同步触发，不证明四轮已到目标，实际速度/状态反馈仍独立上报。
- 原有显式 FIRE_AND_FORGET 配置保留，其成功只代表发送完成；默认仍是 WAIT_ACK，
  本次修复没有切换到无应答策略。广播停车也只需发送完成。
- `9F` 保留原样转发，但不能确认新的命令。`E2/EE` 或运动应答超时冻结后续运动调度，
  由任务取消待发运动并停车。读取仍有原有有限重试；失败运动绝不重放。
- 取消/失败后，新运动等待至少 50 ms 原生运动应答静默窗口，迟到应答会重置窗口。
  接收时还必须满足当前请求已 TXOK、地址和功能码一致。

原生协议没有事务序号，因此对于**静默窗口以后才到达、且地址/功能码完全相同的旧 `02`**，
固件无法从线缆数据中数学上区分新旧；内部 tag 不是驱动器在线缆上返回的序号。
实现避免了已知的其他电机、不同功能、TX 前、旧 `9F` 及失败后短期迟到应答误关联。

| 状态/阶段 | 新行为 | 对外 result |
|---|---|---|
| 接收/入队成功 | 保留命令，不增加执行成功 | 无提前成功 ACK；按钮仍报告接受事件 `0` |
| 收集或等待原生应答 | 内部 pending，继续服务安全/急停 | 不发负 ACK，不增加执行失败 |
| `HAL_CAN_AddTxMessage()` 临时 `HAL_BUSY` | 尚未提交，保留请求等待可用 | 不把等待误判为失败 |
| 主队列/ZDT 队列确实无法接收 | 真正拒绝，保留统计 | ACK `1` |
| 原生 `02`，或允许仅发送确认的请求已 TXOK | 当前请求终态成功 | ACK `0`，执行成功 +1 |
| `HAL_ERROR` / `HAL_TIMEOUT` / `E2/EE` / 安全拒绝 | 保留具体状态、原因；运动停车 | ACK `1`，执行失败 +1；按钮另报事件 `2` |

HAL `HAL_OK/HAL_ERROR/HAL_BUSY/HAL_TIMEOUT` 的数值分别为 `0/1/2/3`，它们不是线缆 result 的直接枚举。
例如终态的 `HAL_BUSY` 仍编码失败 `1`；异步 pending 的 `HAL_BUSY` 不进入 result 编码。
发送层按请求 token 回传真正的 CAN2 HAL/硬件发送失败，并暂停后续提交；
不会把另一帧的总失败计数增量猜测为当前命令失败。

测距采集与有效距离上报代码未改。缺失/无回波/过期距离仍不直接禁止导航，
有效距离、真实接近速度、真实转向、心跳、故障、应答超时和急停保护继续生效。
同批即时帧仍逐帧下发；若实际反馈或完整请求本身确实危险，仍会停车及报告失败。

## 本地诊断

SWD/调试器读取：

- `motor_command_diagnostics[64]`：按 `motor_command_diagnostic_count` 递增的环形记录。
- `motor_last_failure`：保留最近一个具体失败；后续连带取消不覆盖已有根因。
- 原 `can_bus_diagnostics[0/1]`：CAN1/CAN2 队列、HAL 提交及硬件错误统计。

每条命令记录包括 `tick/age_ms/seq/cmd/motor_idx/phase/hal_status/reason/native_result/`
`slave/function/staged_mask/collision_mask`。阶段和原因枚举见 `Core/Inc/motor_control.h`。
保留的 native `E2/EE` 可与具体物理地址和序号对应。不要在读取前复位或重烧固件，否则记录丢失。
这些诊断只驻留 RAM，不新增 CAN 帧或改动现有保留字节。

## 架空实机复测

1. 烧录 `build/motion-result-fix/STM32_Motor_Controller.hex`，保持四轮架空，仍使用现有 ROS。
   同时抓取 0x100/0x102/0x103/0x112 和地址 1～4 的扩展应答。
2. 缓存四轮 `sync=1`，核对每条 ACK 成功均发生在对应 `F6 02 6B` 之后。
   持续正常心跳，等待 2～3 秒后按实体键：应有接受事件、地址 0 的同步广播、
   默认地址 1 的 `FF 02 6B`，随后同序号 `05/result=0`；不应出现事件 `2` 或执行失败增加。
3. 使用现有即时速度测试路径，全部 `sync=0`、5～10 RPM，从前进切换制动和侧移。
   核对每批四轮被收集校验、无 `05` 或合成按钮事件，ACK 与各轮 F6 确认对应。
   用有效近距离验证安全侧移放行、真实朝障碍物运动/旋转停车；无回波时普通导航仍可用，
   恢复有效距离后 ROS 仍能收到距离并参与制动/绕行。
4. 各做一次实体急停/心跳中断；安全条件下模拟一次驱动负应答或丢应答。
   应停车，失败只关联实际序号，不应重放失败运动或随后发出残留同步触发。
   运动期间的指令停止更新超时也须停车。
5. 若再有负 ACK，立即读取 `motor_last_failure` 和环形记录，按同一 `seq` 核对
   `cmd/motor_idx/phase/reason/hal_status/native_result`，同时保存当时距离和速度反馈。
   若原因确为有效距离/真实转向或反馈速度触发保护，应按该证据排查实际运动和测距，不能改成成功。
