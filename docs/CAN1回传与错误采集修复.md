# CAN1 回传与错误采集修复（2026-10-16）

本次处理已离线复现的原生回包丢失和错误分类漏记路径。首次隐性位错误的来源仍未确证，不能据此宣称物理链路已修复。未修改 ROS、运动命令编码、故障停车条件或安全阈值，未烧录。

## 原生回包

此前 CAN2 收到反馈后直接调用 CAN1 普通发送接口并忽略返回值。CAN1 发生发送错误后的 100 ms 退避期，普通接口返回 HAL_BUSY，原生回包因此丢失；随后收到标准 ACK 不能证明这些原生回包已经送达。

现在转入独立 32 帧 FIFO，不与标准应答或周期遥测争用软件队列容量。保持 ID、IDE、RTR、DLC、payload 及原生帧先后顺序，不合并多帧数据。调度优先级为标准应答、原生回包、普通遥测；已进入硬件的帧不被新应答抢占。

原生回包可以在退避期间入队；TXOK 后正常出队，发送错误后保留，继续遵守 100 ms 退避。有效期从 STM32 收到该帧时开始计算，200 ms 后过期，不因重试刷新；已进入邮箱仍未完成的过期请求也会被请求中止。时限依赖发送服务轮询，硬件中止与最后时刻完成发送存在竞争，不承诺严格物理发送截止时刻。

队列满、回包过期及每次实际发送失败继续增加 CAN1 失败总数，`0x103` 格式不变。20 ms 邮箱超时保留未到期回包；显式取消 CAN1 则清空三类待发队列。CAN2 控制命令发送路径不使用此接口，不重放运动命令。长期断链或超量流入仍可能丢帧，不能把有界重试视为送达保证。

## 错误采集

HAL 的通用 CAN IRQ 函数在 RX0 入口执行时，也可能处理错误并清除 ESR.LEC。此前只在 SCE 入口保存错误，存在 RX0 提前清除分类的路径。

现在 CAN1/CAN2 的 SCE、RX0 入口都先调用错误采集。仅在 MSR.ERRI 挂起时记录，因此普通 RX 中断和已被另一入口处理的过期 SCE 不会重复计数或覆盖最近错误。计数仍表示中断入口观察到的错误／状态通知，不等同于每一个物理错误。

SWD 诊断格式由 2 升为 3，在原字段后追加：

| 字段 | 含义 |
|---|---|
| forward_pending | 原生回包待发数，包含在途队首 |
| forward_retries | 原生回包邮箱错误或 20 ms 超时后的保留次数 |
| forward_overflow | 原生 FIFO 满导致拒绝的帧数 |
| forward_expired | 以首次接收时间计算的过期帧数 |

`tools/observe_can_swd.py` 根据对应 ELF 的符号大小识别格式 2/3，并核对两路运行版本。重新编译后必须使用实际烧录的 ELF，不能沿用旧诊断地址。

## 验证与产物

运行 `python tools/run_host_tests.py`：覆盖真实 CAN2 接收转发、退避期间入队、标准 ACK 优先、分片顺序、邮箱错误／超时恢复、接近截止时间的在途过期、持续失败的重试上限、溢出计数、取消、时钟回绕及仲裁失败。错误采集回归覆盖两路 RX0 抢先处理、过期 SCE 不覆盖、普通 RX 不计错和纯状态通知。现有急停、运动有效期、反馈新鲜度和碰撞停车回归一并执行。

最终结果：CAN／控制原生回归、生产运动学及未配置保护回归通过，33 项 Python 测试全部通过。60 秒默认负载仿真送出标准 ACK 600 条、原生回包 3000 条，最大延迟分别为 10 ms、11 ms，普通队列高水位 22，失败计数为 0。这些数值来自主机仿真，不代表实机总线表现。

正常应用构建命令：

```powershell
cmake -S . -B build/can1-feedback-fix -G Ninja '-DCMAKE_TOOLCHAIN_FILE=cmake/gcc-arm-none-eabi.cmake' '-DCMAKE_BUILD_TYPE=Debug' '-DSTM32_DIAGNOSTIC_CAN_PROBE=OFF' '-DSTM32_DIAGNOSTIC_HSI_CLOCK=OFF' '-DSTM32_DIAGNOSTIC_HSE_DIRECT=OFF'
cmake --build build/can1-feedback-fix --parallel 4
```

固件：`build/can1-feedback-fix/STM32_Motor_Controller.hex`；对应 ELF 为同目录同名 `.elf`。
正常应用编译通过，FLASH 使用 63428 B，RAM 使用 31984 B；ELF 中双路诊断符号大小为 368 B，与格式 3 一致。
以上均为离线验证，不能替代后续实机对 CAN1 位错误及完整路线的复测。
