# 硬件接线总览

本文整理 STM32_Motor_Controller 工程涉及的全部硬件接线。所有内容以固件实际配置为准，
对应文件：`Core/Inc/main.h`、`Core/Inc/distance_sensor.h`、`Core/Inc/arm_servo_config.h`、
`Core/Src/distance_sensor.c`、`Core/Src/main.c`、`STM32_Motor_Controller.ioc`。

## 1. 控制器与时钟

| 项目 | 值 |
|---|---|
| MCU | STM32F407VET6（LQFP100） |
| 外部晶振 | 8 MHz（PH0-OSC_IN / PH1-OSC_OUT） |
| 系统主频 | 72 MHz（PLLM=8, PLLN=144, PLLQ=3） |
| AHB / APB1 / APB2 | 72 MHz / 36 MHz / 36 MHz |
| 定时器时钟 | APB1、APB2 定时器均为 72 MHz |

### 1.1 时钟与时基核查

下表以**实际 HSE=8 MHz**为前提；当前源码与 `.ioc` 的时钟配置一致，运行期间没有切换主频。

| 使用方 | 时钟／分频 | 结果与占用 |
|---|---|---|
| PLL | 8 MHz / 8 × 144，P=2，Q=3 | VCO=144 MHz，SYSCLK=72 MHz，Q 输出=48 MHz |
| CAN1 / CAN2 | PCLK1=36 MHz，分频 6，每位 12 tq | 500 kbit/s，采样点约 83.3%；CAN 不使用定时器倍频 |
| TIM3 / TIM4 | APB1 定时器=72 MHz，PSC=719，ARR=1999 | 50 Hz 舵机 PWM，由硬件持续输出 |
| TIM8 | APB2 定时器=72 MHz，PSC=71，ARR=19999 | 50 Hz 舵机 PWM；由 `ArmServo_Init()` 独立初始化 |
| HAL 时基 | TIM6=72 MHz，PSC=71，ARR=999 | 1 kHz，仅 TIM6 回调调用 `HAL_IncTick()` |
| FreeRTOS 时基 | SysTick=HCLK，LOAD=71999 | 1 kHz，CMSIS 包装层调用 `xPortSysTickHandler()`，不重复递增 HAL tick |
| I2C1 | PCLK1=36 MHz，快速模式，CCR=30，TRISE=11 | 标称 400 kHz；配置和出错恢复均写死当前时钟参数 |

HAL 初始化时先按复位时钟启动 TIM6，`HAL_RCC_ClockConfig()` 更新 `SystemCoreClock` 后会重新
配置 HAL 时基，随后 FreeRTOS 才配置 SysTick。因此初始 `SystemCoreClock=16 MHz` 不代表
调度器一直按 16 MHz 运行。TIM1 为编码器，TIM3/TIM4/TIM8 为 PWM，TIM6 为 HAL 时基，
未发现重复占用同一定时器。

时序风险需与 CAN 位错误分开判断：

- **硬件晶振未确认**：CAN、I2C 和固定 PWM 分频都依赖当前时钟。切换板型宏不会切换 PLL，
  修改 `HSE_VALUE` 也不会改变硬件频率。换板／改频必须同时复核这些配置。
- **时基中断可被延迟**：CAN RX0 优先级为 5，TIM6 和 SysTick 为 15；CAN 中断持续排空 FIFO，
  部分驱动操作使用全局关中断。高负载下可能推迟时基和任务执行，尚未实测持续时间；
  未发现这些关中断路径中有等待 HAL tick 推进的阻塞循环。调度延迟和接收溢出不能直接解释
  CAN 控制器报告的大量 CRC／格式／位填充错误。
- **启动顺序已避开时基阻塞**：传感器初始化及其 `HAL_Delay()` 在 RTOS 对象创建前完成；
  CAN 启动在调度器启动后执行，未发现启动前被 RTOS 临界区屏蔽 TIM6 后再等待 tick 的路径。

### 1.2 已复现的位置轮询与有效期不匹配

`StartStatusTask()` 每轮最多查询一次，延迟 20 个 RTOS tick；`motor_update_status()` 将速度
查询与状态／位置查询交替安排。使用实际 CAN／控制源文件、模拟即时应答，连续执行 40 轮
20 ms 查询，四台电机均得到：**速度更新间隔 160 ms，位置更新间隔 320 ms**。
`CHASSIS_FEEDBACK_FRESH_MS` 则只有 **200 ms**。

因此，即使通信正常，位置反馈也会周期性过期，影响 `slot_to_speed()` 中需要新鲜位置的绝对
位置（mode=1）和基于前次目标的位置（mode=0）命令。四轮位置采样横跨约 240 ms，超过
200 ms，在上述理想轮询条件下也不能同时满足四轮位置新鲜度，影响这两类同步位置指令。
运动指令还会中断后台读取等待，实际刷新间隔可能更长。

这是一处业务时序不匹配，**不是已确认的 ERROR-PASSIVE 根因**。修复方向是协调位置查询
频率与安全有效期，并验证四轮同步位置指令；本次核查未修改固件或放宽安全阈值。

## 4. CAN1 —— 与 ROS 上位机通信

| 信号 | STM32 引脚 | 外部器件 |
|---|---|---|
| CAN1_RX | PD0 | CAN 收发器 RXD |
| CAN1_TX | PD1 | CAN 收发器 TXD |

2026-10-16：用户报告 PA11/PA12 短接击穿，CAN1 已迁移到 PD0/PD1（AF9）。
接线前断电，断开原 PA11/PA12 与收发器的连接；确认收发器正常后，将 RXD 接 PD0、
TXD 接 PD1。PD0/PD1 是逻辑信号，不能直接连接 CANH/CANL。当前应用未占用这两个
引脚，仍需确认实际板卡已引出且无板载外设冲突。PB8/PB9 继续用于测距 I2C。
更换引脚不能保证解决 MCU 内部或收发器损坏，外部通信恢复须另行实测。

本次已编译并通过 ST-Link 烧录完整应用固件
`build/can1-pd0-pd1/STM32_Motor_Controller.hex`（三个诊断选项均为 OFF），
OpenOCD 返回 `Verified OK` 后复位。烧录前 512 KiB Flash 备份为同目录的
`flash-before.bin`。读回 GPIOD_MODER=`0x2000000A`、GPIOD_AFRL=`0x00000099`，
确认 PD0/PD1 均为 AF9；GPIOA_MODER=`0xA8000000`，PA11/PA12 未配置为复用输出；
CAN1_BTR=`0x00180005`，HAL tick 持续递增。烧录及寄存器记录见同目录
`flash.log`、`runtime-check.log`。完整应用及最小诊断版本均编译通过，现有主机
CAN/控制回归与 30 项 Python 测试通过；本次未验证新接线后的外部 CAN 收发。

- 位率：**500 kbit/s**（APB1=36 MHz，Prescaler=6，BS1=9 tq，BS2=2 tq，SJW=1 tq）。
- 模式：Normal，CAN1 关闭硬件自动重发、开启自动 Bus-Off 恢复；发送错误后退避 100 ms。
- 滤波器：Bank 0，FIFO0，收**全部**帧。
- 帧格式：标准帧。
- 上位机用到的 ID：
  - `0x100` 命令（ROS → 板）
  - `0x101` 状态（板 → ROS）
  - `0x102` ACK
  - `0x103` 统计
  - `0x110` 距离数据
  - `0x111` 传感器诊断
  - `0x112` 物理按键事件
- 硬件要求：总线上**两端各接一个 120 Ω 终端电阻**。

> 本工程没有控制 CAN 收发器的 STB/EN 引脚，因此必须由模块硬件将收发器保持在正常工作模式，
> 不能据此推断模块为常使能型。按实际型号及模块原理图确认控制脚电平：高有效 STB 通常应拉低
> 才能退出待机，EN 的有效电平另行确认；SN65HVD230 的 RS 脚也需按手册配置。不要一律拉高 STB。

### 4.1 ROS 通信错误排查（2026-10-16 更新）

详见 [CAN 最小程序诊断](CAN最小程序诊断.md) 和 [CAN 发送风暴修复](CAN发送风暴修复.md)。
本次恢复调试连接后，读回 CAN1 MCR=`0x00010054`、BTR=`0x00180005`、
ESR=`0x00800033`，确认已关闭硬件重发，但仍有 ACK 错误（TEC=128、REC=0）。
没有新增总线模拟波形证据。
已确认 CANable 断连为手动操作，因此这次断连本身不作为 USB／虚拟机故障证据。
原始日志已核查，见 [CAN 原始日志分析](CAN原始日志分析_20261015.md)：其中还存在位时序
设置超时、主机发送失败和后期已成功接收 STM32 数据等不同阶段的证据。

| 检查项 | 源码结论与限制 |
|---|---|
| 位率 | `main.c` 使用 HSE、PLLM=8、PLLN=144、PLLP=2、APB1 分频 2；`stm32f4xx_hal_conf.h` 和 `.ioc` 均声明 HSE=8 MHz。实际晶振为 8 MHz 时，CAN 时钟为 36 MHz，位率为 `36 MHz / (6 × (1+9+2)) = 500 kbit/s`，采样点约 83.3%。CAN 使用 APB1 外设时钟，不使用翻倍后的定时器时钟。 |
| 实际晶振 | 此前 HSE 直接作系统时钟的粗测估计约 8.0004 MHz，足以区分 8/25 MHz，不能代替精密校准。此前读回 BTR 为 `0x00180005`。换板或重新烧录后仍应核实；仅切换 `SERVO_ACTIVE_BOARD` 不会切换 PLL。 |
| 失败后的积压 | 当前 CAN1 关闭自动重发，只保留一个硬件发送请求；发送错误后退避 100 ms，普通 FIFO 提交期间返回 `HAL_BUSY`，周期最新值、独立应答和原生回包仍可有界入队；挂起超过 20 ms 时中止请求、清空普通积压，保留未到期应答和原生回包。持续发送失败时尝试约每秒 10 次。CAN2 仍保留自动重发。两路普通发送队列各 64 帧。 |
| 错误可见性 | CAN1/CAN2 的 SCE、RX0 入口均在 HAL 清除 LEC 前检查 `MSR.ERRI` 并保存 ESR、时间及事件数；普通接收或过期中断不覆盖已保存错误。SWD 诊断格式为 3，新增原生回包待发、重试、溢出、过期统计；读取工具兼容格式 2/3。`HAL_CAN_GetState()==LISTENING` 仅为 HAL 软件状态，发送服务另检查 ESR.BOFF。 |
| 现有统计 | `0x103` 类型 `0x03` 中的 CAN1 失败计数包含队列满、HAL 提交失败、邮箱发送失败、挂起超时及应答／原生回包过期，普通提交在退避期间的拒绝不逐次计数；CAN2 字段还叠加驱动等待队列拒绝计数。它们都不是 TEC/REC，也不逐次统计硬件自动重发。报文格式未变；统计本身经 CAN1 发送，断链时也可能无法送达。 |
| 应用应答 | 已将执行应答、命令拒绝应答和舵机应答移至独立的 32 帧优先队列，退避期间也可入队。失败后按 100 ms 退避重试，最长保留 500 ms；只重发应答，不重新执行命令。自身容量耗尽或过期仍可能丢失，分别记录 `reply_overflow`、`reply_expired`。这修复遥测挤掉应答的路径，不能代替修复 CAN 硬件 ACK。 |
| 原生反馈转发 | CAN2 → CAN1 使用独立 32 帧 FIFO，退避期间接受入队，只有 TXOK 后正常出队；失败后有界重试，接收起满 200 ms 则过期，已挂起邮箱也请求中止。按标准应答、原生回包、普通遥测顺序调度；不合并分片、不重发运动命令。容量溢出或过期仍增加失败统计。 |
| ROS 后果 | ACK、状态和测距上报可能延迟或丢失；有效上位机消息超过 500 ms 未被接收时，会触发心跳超时停机。是否对应现场 ROS 报错，仍需日志确认。 |

以上回传与错误采集修复已通过离线回归和正常应用构建，固件位于
`build/can1-feedback-fix/STM32_Motor_Controller.hex`，本轮未烧录或上板复测。
详见 [CAN1 回传与错误采集修复](CAN1回传与错误采集修复.md)。物理位错误的首次来源仍未确证。

`ERROR-PASSIVE` 表示 CAN 控制器发送或接收错误计数达到被动错误阈值（128），与软件队列满是
不同机制。普通仲裁失败和软件排队不应直接产生大量 CRC、格式或位填充错误。主机报告的
`No buffer space available` 也不能直接等同于 STM32 的 64 帧队列满，应结合报错位置和两端状态判断。

本次用户确认：仅连接 STM32 CAN1、收发器和 USB-CAN，ROS 未启动，STM32 上电后仍出现
大量错误。正常应用的状态任务会主动周期发送，不依赖 ROS 命令；默认四台电机各三类状态、
周期约 20 ms，健康时仅 `0x101` 即约 600 帧/秒。上电触发错误不能单独确定损坏部件。
USB-CAN 在接口 UP、正常模式、位率匹配且总线有效时应由硬件自动 ACK，不需要 ROS
应用运行；接口 DOWN、静默模式或 Bus-Off 时不能期待它正常确认。
此前最小程序内部回环 32/32 通过，外部发送仍出现 ACK 错误，说明正常应用任务并非该故障
的必要条件。应优先核查当前接口模式及外部双向链路，而不是把 `0x102` 丢失视作硬件 ACK 根因。

优先进行以下现场核查：

1. **确认实际时钟**：核对晶振丝印、板卡原理图及烧录版本。检查运行中的 RCC 配置和 CAN BTR，
   当前配置的 BTR 预期为 `0x00180005`；寄存器值仍不能证明外部晶振频率，须结合实测时钟。
   用示波器／逻辑分析仪验证标称位时间约为 **2 μs**，或通过合适的 MCO 测量时钟。
2. **检查 CAN1 物理层**：总线断电后，两个 120 Ω 终端并联时 CAN_H 与 CAN_L 间通常约为
   **60 Ω**；检查 H/L、信号地、接头、短分支、收发器供电及正常模式控制脚。CAN1 与 CAN2
   是独立总线，需分别检查，CANable 接 ROS 所在的 CAN1。
3. **采集同一时段日志**：Linux ROS 主机执行下列只读命令（按实际接口名替换 `can0`），保留
   首次错误、缓冲区满前后的计数变化。`candump` 的错误详情取决于适配器和驱动支持。

   ```bash
   ip -details -statistics link show can0
   candump -t a -e 'can0,0:0,#FFFFFFFF'
   journalctl -k -f -o short-precise
   ```

   主机 `bus-errors`、error-passive／bus-off、TEC/REC（如驱动提供）、丢包和溢出应分别记录；
   主机适配器的错误计数与 STM32 的错误计数也不是同一组。记录 ROS 报错时间以便对齐。

已有主机回归覆盖邮箱阻塞、HAL 提交失败、队列拒绝及四电机 50 Hz 指令，当前全部通过。
模拟 HAL 测试不能验证晶振、收发器、终端、真实错误帧或 USB 透传，不能据此排除硬件问题。

## 5. CAN2 —— ZDT Y42 闭环步进电机

| 信号 | STM32 引脚 | 外部器件 |
|---|---|---|
| CAN2_RX | PB12 | CAN 收发器 RXD |

- 位率同为 **500 kbit/s**。
- 滤波器：Bank 14，FIFO0，收**全部**帧。
- 帧格式：**扩展帧**（Modbus-RTU over CAN）。
- 电机从机地址默认 `{1, 2, 3, 4}`（`Core/Src/motor_control.c:15`），对应 4 个底盘电机 ID 0~3；

两块板间无电气隔离要求时须共地。

## 6. I2C1 + 六路 VL53L1X 距离传感器

### 6.1 公共总线（六路共用）

| 信号 | STM32 引脚 | 接线 |
|---|---|---|
| SCL | PB8 | 六个模块 SCL 并联 |
| SDA | PB9 | 六个模块 SDA 并联 |
| VCC | — | 3.3 V |
| GND | — | 共地 |

固件在 `distance_sensor.c` 中自行配置 I2C1 寄存器，不使用 HAL 的 I2C 句柄。

**上拉电阻**：SDA、SCL 各需一个外部上拉到 3.3 V（典型 4.7 kΩ）。六路并联后总线总上拉
不宜大于 3~4 kΩ，否则上升沿过缓会通信不稳定。

### 6.2 各路 XSHUT 与 I2C 地址

| ID | 位置 | XSHUT 引脚 | 分配的 I2C 地址（7 位） |
|---|---|---|---|
| 0 | FRONT 前 | PE0 | 0x30 |
| 1 | LEFT 左 | PE1 | 0x31 |
| 2 | RIGHT 右 | PE2 | 0x32 |
| 3 | ARM_UPPER_LEFT 机械臂左上 | PE5 | 0x33 |
| 4 | ARM_UPPER_RIGHT 机械臂右上 | PE6 | 0x34 |
| 5 | REAR 后 | PE7 | 0x35 |

模块上电默认地址是 `0x29`（`VL53L1X_DEFAULT_ADDR`）。

### 6.3 接线注意事项

1. **XSHUT 极性**：VL53L1X 模块的 XSHUT 是**低电平复位**。固件中
   `sensor_set_xshut(sensor, GPIO_PIN_SET)` 表示唤醒，`GPIO_PIN_RESET` 表示复位。
   **每路 XSHUT 必须接对应 GPIO**：固定接 GND 会一直复位；全部固定接 3.3 V 会导致
   默认地址 `0x29` 冲突，无法逐路初始化和重新分配地址。型号 ID 应为 `0xEACC`。
2. **地址由固件分配**：每次 `distance_sensor_init()` 会逐路复位后向 `0x0001` 寄存器写入新
   地址（`distance_sensor.c:516`）。所以模块插在哪个物理位置都可以，只要 XSHUT 接对引脚。
3. **供电方式**：固件会打开 `EXTSUP`（外部供电）配置位（`distance_sensor.c:450-451`），
   模块 VCC 应接 3.3 V。
4. 六个 XSHUT 全部在 GPIOE 上，PE3/PE4 已被板载按键占用，插线时注意不要错位。

### 6.4 上电上报与故障恢复（2026-10-16）

- 六路正常运行时持续上报 CAN1 标准帧 `0x110`，测量周期 50 ms，任务每 5 ms 轮询一路。
- 初始化失败或缺少新结果时，上报无效距离 `0xFFFF`，并清除 VALID；无效距离与 `0x111`
  诊断至少按约 1 s 的间隔重新通告，便于晚启动的 ROS 发现故障。不能把这些帧当作有效测距。
- 故障模块约 1 s 后进入重试；每次只对一个模块进行 XSHUT 复位、等待启动、分配地址和
  重新配置，复位和启动等待拆分到多次轮询，其他模块继续采样。断线、接错型号等硬件问题
  不会被软件重试变成有效距离。
- 电机状态 `0x101` 默认上报掩码改为 `0x07`，包括 `01` 基本状态、`02` 位置、`03` 速度。
  四路每约 20 ms 上报一次，总计约 600 帧/s，另有测距和统计帧。
- ROS 的 `0x100` 命令 `07` 仍能修改电机状态掩码；若 ROS 设置 `0x01`，就只发 `01`
  类型，且不影响独立的 `0x110/0x111`。恢复三种状态可执行
  `cansend can0 100#07FF070000000000`；需要同步修改持续发送旧掩码的 ROS 配置。
- 同一电机选中的状态类型作为一批入队，队列空间不足时整批跳过，下一周期重报，避免
  拥堵时反复只接受 `01`。这不保证物理总线故障时每帧都能送达。

烧录新固件后，在主机运行 `candump -t a 'can0,110:7FF,111:7FF'`。正常传感器应持续有
`0x110` 有效数据；即使六路都未接，稍后开始抓包也应看到周期性的无效距离与诊断。

## 7. 舵机 PWM

工程中存在**两套**舵机驱动，通过 `Core/Src/main.c:52` 的 `SERVO_ACTIVE_BOARD` 选择：

```c
#define SERVO_BOARD_STANDARD 1U   // PB0 / PD14 两路机械臂舵机，支持 CAN 控制
#define SERVO_BOARD_CAM      2U   // PC6/PC7/PC8 摄像头板舵机
#define SERVO_ACTIVE_BOARD   SERVO_BOARD_STANDARD   // 当前选择
```

两套驱动无论选哪一套都会初始化，因此以下引脚在当前固件中都可能输出 PWM。

### 7.1 标准板舵机（TIM3 / TIM4）

| 信号 | STM32 引脚 | 定时器通道 |
|---|---|---|
| 机械臂舵机 1 | PB0 | TIM3_CH3 |
| 机械臂舵机 2 | PD14 | TIM4_CH3 |

- 定时器时钟 72 MHz，Prescaler = 720-1 → 计数频率 100 kHz，Period = 2000-1 → **PWM 频率 50 Hz**。
- 脉宽范围：55 ~ 250 tick → **550 μs ~ 2500 μs**（`SERVO_PWM_MIN/MAX_TICKS`，`main.c:46-47`）。
- 舵机需**共地**：舵机 5 V 电源地必须与 STM32 GND 连通，否则 PWM 抖动或完全无响应。
- 舵机电源**不要**从 STM32 的 5 V/3.3 V 引脚取电，舵机堵转电流会拉垮 MCU。

### 7.2 摄像头板舵机（TIM8，arm_servo）

| 逻辑通道 | STM32 引脚 | 定时器通道 | 用途 | 方向 |
|---|---|---|---|---|
| CH1 | PC6 | TIM8_CH1 | 右臂主舵机 | +1（增脉宽） |
| CH2 | PC7 | TIM8_CH2 | 左臂主舵机 | −1（减脉宽） |
| CH3 | PC8 | TIM8_CH3 | 右臂第二只，跟随 CH1 | 同 CH1 |
| CH4 | PC9 | TIM8_CH4 | 已配置，**固件不启动** | — |

- PWM 频率：`ARM_SERVO_FRAME_US = 20000` → **50 Hz**。
- 脉宽：`500 ~ 2500 μs`，逻辑零位 `1500 μs`，行程 `180°`。
- 软件角度限位：**−80° ~ +80°**。这是软件边界，**不代表**实测机械臂安全间隙，
  首次通电前请先用 +5° 小角度验证方向（`arm_servo_config.h:20-24`）。
- 当前舵机型号配置为 **DS3230MG**（`ARM_SERVO_KEY_TEST_ENABLE = 1`）。若换成 SG90，
  需把该宏改为 0，并重新确认脉宽范围是否满足 SG90（常见 500~2400 μs）。

### 9.1 标准板（当前启用，`SERVO_ACTIVE_BOARD = SERVO_BOARD_STANDARD`）

## 10. 电源

| 负载 | 建议供电 |
|---|---|
| STM32 板 | 3.3 V 主输入（板上稳压后供 MCU 与 I2C 设备） |
| VL53L1X ×6 | 3.3 V |
| 舵机 ×3~5 | 独立 5~6 V 大电流电源，**必须与 MCU 共地** |
| ZDT Y42 步进电机 | 独立电机电源（按电机额定电压），**必须与 MCU 共地** |
| CAN 收发器 | 随 CAN 规范，注意逻辑侧与总线侧电压匹配 |

共地是重点：舵机电源、电机电源、MCU 三者若不共地，CAN 会出现莫名其妙的帧错误、
PWM 抖动、I2C 读数漂移。
