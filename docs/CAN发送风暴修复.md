# CAN1 重复首帧风暴修复（2026-10-16）

## 定位结果

`101 [8] 01 00 00 00 00 00 00 00` 是标准状态帧：类型 1、
电机索引 0、状态和故障字段为零。字段为零本身不证明电机已经正常工作。
正常应用每约 20 ms 上报四台电机，默认每台有基础状态、位置、速度三种类型，
因此健康链路本来也会有约 600 帧/秒的 `0x101`；其中同一台电机的同一类型约 50 帧/秒。
仅凭六行相同数据不能判断是否异常，必须结合帧间隔和发送控制器状态。

本次通过 ST-Link 读取当前运行的旧固件，得到：

| 项目 | 修复前实测 | 含义 |
|---|---|---|
| CAN1 MCR | `0x00010044` | NART=0，允许硬件自动重发 |
| CAN1 TSR | `0x82000008` | 三个发送邮箱都未空闲 |
| CAN1 ESR | `0x00800033` | TEC=128、LEC=3（ACK 错误）、错误被动 |
| 三个邮箱 TIR | 都为 `0x20200001` | 标准 ID `0x101`，TXRQ=1 |
| 三个邮箱数据低字 | `0x00000001 / 02 / 03` | 三类状态均已请求发送 |

证据确认当前发送无法正常完成，且存在硬件持续重发路径。重复帧来源不只是
状态任务的周期调用；软件没有对无 ACK 时的硬件重发设置边界。
本次没有据此断言 USB-CAN、收发器或某一根线已经损坏。

## 修改

- CAN1 关闭硬件自动重发，使用单次发送；同步 CubeMX 配置 `CAN1.NART=DISABLE`。
- 发送层观察每次发送的实际邮箱结果。发送错误计入失败统计，错误帧不重新入队，
  暂停发送 100 ms；退避期间新入队请求返回 `HAL_BUSY`。
- CAN1 同时只保留一个硬件发送请求，防止 HAL 重用邮箱后丢失上一帧的结果。
- 单次发送仅因仲裁失败时，保留队首帧，在下一次发送服务中继续尝试。
  正常仲裁失败不触发链路错误退避，也不使后续 ACK 越过前帧。
- 请求超过 20 ms 仍挂起时，中止 CAN1 请求并清空其积压队列，再进入退避。
  这覆盖总线一直无法进入空闲或 Bus-Off 时请求无法结束的情况。
- CAN2 保留现有重发和队列处理方式，其服务不受 CAN1 退避阻塞。

持续发送错误时，CAN1 的发送尝试被限制在约每秒 10 次。正常发送仍使用原有
状态周期和报文格式。错误时不保证 ACK/事件送达，ROS 仍须按超时处理通信失败；
发送层返回 `HAL_OK` 仍仅表示软件队列接受。

`can_transport_get_failure_count()` / `0x103` 的发送失败统计同时包括队列满和
发送错误，不能直接用其增量计算物理总线发送次数。

## 验证与烧录

执行 `python tools/run_host_tests.py`：原生 CAN/control 回归、生产底盘配置回归、
未配置底盘保护回归，以及 30 项 Python 测试均通过。
新增行为验证覆盖持续无 ACK 的发送次数上限、CAN2 独立运行、故障恢复、
邮箱卡住、HAL 提交失败、时钟回绕及仲裁失败后的保序重试。

正常应用固件已重新编译并通过 ST-Link 烧录，OpenOCD 返回 `Verified OK` 后复位：

- 固件：`build/vl53-recovery/STM32_Motor_Controller.hex`。
- 三个 `STM32_DIAGNOSTIC_*` 选项均为 OFF。
- HEX SHA256：`14681AB098E3F9C11009C496E2411A7E820E2982B237DD433379D85E74ECC47E`。
- 烧录前板上 Flash 已备份为 `build/can-storm-before.bin`，起始地址 `0x08000000`。

最终固件运行中，间隔约 5 秒两次读取均得到：

| 项目 | 修复后实测 | 含义 |
|---|---|---|
| CAN1 MCR | `0x00010054` | NART=1，硬件重发关闭 |
| CAN1 TSR | `0x1C000009` | 三个邮箱均空闲，上次发送以错误结束 |
| CAN1 ESR | `0x00800033` | ACK 错误仍存在 |

这确认固件已切断无限重发路径，且邮箱不再像旧固件一样持续挂起。
每秒约 10 次的上限由发送逻辑和模拟故障回归验证；本次未在 ROS 主机实测帧率。
链路仍未获得 ACK，因此不能把本次防风暴修复视作外部通信已经恢复。

## ROS 端复核

保持正常 500 kbit/s 模式，抓取业务帧和错误帧，保留接口统计：

```bash
timeout 5s candump -t d -e 'can0,0:0,#FFFFFFFF'
ip -details -statistics link show can0
```

错误链路下应不再连续无间隔地重发首帧；可能收到少量帧，也可能完全收不到。
健康链路下应恢复多种 `0x101` 状态和 `0x110/0x111`，周期重复状态仍属正常行为。
是否恢复通信，需要同时确认主机错误统计和 STM32 的发送成功/ACK 状态。
