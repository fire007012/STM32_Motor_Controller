## 结论

现有材料确认 CANable 曾报告 CAN 协议错误和 ERROR-PASSIVE，ROS 曾出现主机发送失败、
接收超时和急停。它们支持链路／位时序异常使发送受阻的解释，但不能确证完整因果顺序：
`candump` 和 `ip link` 摘录没有时间戳，也不是连续抓包。

另有两条独立线索：gs_usb 设置位时序时出现 USB 控制请求超时；ROS 在早期发送失败后
约每 100 ms 重新绑定 SocketCAN。后期已有 STM32 数据被成功接收，故不同阶段不能合并
成一次持续断链。此前发现的位置轮询 320 ms／有效期 200 ms 不匹配，不能解释这些 CAN
协议错误；本批日志也没有给出位置命令因该问题被拒绝的直接证据。

## CAN 错误与位时序

- [接口快照](../can-raw-logs-20261015/can-raw-logs-20261015/ip-link-session-excerpt.txt)：
  第 7 行为 `ERROR-PASSIVE`；第 8–11 行为 500000 bit/s、采样点 87.5%、tq=125 ns、
  适配器时钟 48 MHz。`1+6+7+2=16 tq`，`16 × 125 ns=2 μs`，主机配置计算正确。
  STM32 当前源码采样点为 83.3%，两者不同本身不构成配置冲突；控制器时钟也无需相同。
- 第 12–17 行的 `error-warn=48481`、`error-pass=144521` 是驱动累计统计，不能当作
  TEC/REC 当前值，也不能等同于同样数量的唯一坏帧。该快照 `bus-off=0`、`restart-ms=0`，
  不能把本次 ERROR-PASSIVE 直接解释为进入 Bus-Off 后未自动重启。
- 快照 RX packets=194522，TX packets=0。SocketCAN 接收包可能包含错误帧，因此不能
  把 RX 包数当作成功收到同样数量的 STM32 应用报文；TX=0 也仅描述该接口快照统计。
- [错误帧摘录](../can-raw-logs-20261015/can-raw-logs-20261015/candump-session-excerpt.txt)
  第 5–13 行明确出现 CRC sequence、frame format、bit stuffing 错误以及被动错误标志。
  这是 CANable／驱动报告的总线协议错误，不能归因于 ROS 应用队列满或普通仲裁等待。
  它不是 STM32 ESR 记录，不能据此给出 STM32 自身错误计数或断定哪一端损坏。

## USB／适配器证据

[内核原始日志](../can-raw-logs-20261015/can-raw-logs-20261015/kernel-original.log) 第 33、34、
56–60、73、74、94 行，共 **10 条** `Couldn't set bittimings (err=-110)`，发生于
16:01、16:15、16:21、17:29。`-110` 为超时，gs_usb 在将位时序参数下发给适配器的
控制路径上失败；它不是 STM32 的 CAN 位时序寄存器报错，也不是 ROS 速度命令超时。
应检查 CANable 固件、USB／虚拟机透传及适配器响应，不能仅凭此确定是哪一个环节。

用户已确认断连是手动操作。断连后的 `Couldn't shutdown device (err=-19)` 可由设备
已拔出解释，不作为异常断连证据。但手动断连不消除前述“设置参数超时”的独立线索。

ENOBUFS 也发生在对应拔出之前：17:36 的报错早于 17:41:50.581 拔出；18:49 的报错
早于 18:50:18.303 拔出。手动拔出不能解释这些更早的失败。错误帧摘录无时间戳，不能
进一步声称“某次 USB 断连先导致 CRC 错误”。

## 下一步定位

1. 先核实 STM32 实际晶振、烧录版本、运行中的 RCC/CAN BTR 和 2 μs 标称位时间；同时检查
   CAN1 收发器正常模式、供电、信号地及断电时约 60 Ω 的终端等效电阻。源码的 500 kbit/s
   与主机配置一致，仍不能代替实测。
2. CANable 在原生 Linux USB 环境与当前虚拟机环境做相同配置测试，记录位时序设置是否仍
   超时；若设置阶段就失败，先解决适配器控制路径，再评价后续收发结果。
3. 同时保存带时间戳的完整 `candump -t a -e 'can0,0:0,#FFFFFFFF'`、多次 `ip -details
   -statistics link show can0`、`journalctl -k -f -o short-precise` 及 ROS 日志。给接口
   快照额外记录采样时间；记录 STM32 ESR/TSR，以区分两端错误计数及主机／固件队列。
4. 检查 ROS `openSocket()`／`sendCanFrame()` 的发送失败恢复，确认是否每 100 ms 重开
   socket、是否重复发送探测、如何区分 ENOBUFS/EAGAIN/设备移除，以及恢复期间如何保留急停。
   本仓库不含这份 ROS 节点源码，本次只能确认日志行为，尚未验证其实现。
5. 后期单独检查 `CACHE_READY → 启动请求 → 0x102 ACK → RUNNING` 的完整链路、CAN2
   真实电机回包，以及 18:56 的否定急停 ACK。记录 0x103 各类型计数原值，不能把所有失败
   计数变化都解释为物理层错误。位置轮询时序不匹配另行修复和验证。

本次为离线日志与源码核对，未改动固件、原始证据或现场 CAN 配置。
